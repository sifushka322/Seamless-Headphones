# Сценарии Seamless Headphones 0.2

## Ориентир Apple и наш продукт

Apple описывает автоматический переход совместимых AirPods между устройствами с одним Apple Account и двухфакторной аутентификацией при начале нового воспроизведения; текущий разговор защищён от переключения. Это поведение совместимой экосистемы, а не стандарт для любых Bluetooth-наушников. [Apple Support](https://support.apple.com/en-au/104988).

Наш Mac координирует передачу с Android через BLE. Наушники не знают об этом протоколе: приложения управляют системными аудиоподключениями. Общая Wi-Fi сеть и интернет не нужны. Обычные наушники и ограничения Android не позволяют заранее обещать скорость или бесшовность AirPods.

## Правила версии 0.2

| Сценарий | Поведение |
|---|---|
| Телефон просто лежит рядом | Не переключать |
| Новая музыка в разрешённом приложении | После 2–5 с устойчивой активности запросить передачу |
| Режим «только в паузе» | Не забирать звук у активного источника; для новой попытки нужен новый Play |
| Обычное уведомление / краткий звук | Не является Android media trigger; на Mac действует список источников и debounce |
| Реклама в разрешённом плеере | Может выглядеть как воспроизведение; семантически не распознаётся |
| Оба устройства начинают одновременно | Одна транзакция; при событиях в одном такте приоритет Mac |
| Ручная передача | Две минуты приоритета; события внутри этого окна не откладываются на потом |
| Звонок / активный микрофон | Блокировка по доступным сигналам ОС; Android без права читать состояние вызова не включает авто |
| Удержание на любой стороне | Блокировка обеих сторон |
| Устройство уже владеет подтверждённым маршрутом | Повторная передача не нужна |
| Устаревшее состояние второго устройства | Блокировка, запрос новых состояний |
| Переподключение / запуск / изменение настроек | Уже активное воспроизведение становится исходным состоянием, не запускает передачу |
| Ошибка адаптера / тайм-аут | Пауза автоматики до явного возобновления |
| Потеря BLE | Остановить транзакцию, не переключать вслепую, ограниченно повторять поиск |
| Сон Mac | Остановить BLE; после пробуждения восстановить, если включено |
| Выключенные наушники / разные выбранные устройства | Отказ с причиной; не объявлять успех |

## Источники и наблюдение

Mac: CoreAudio process objects показывают активность входного и выходного потока каждого процесса. Это не Now Playing и не измерение слышимой громкости. Некоторые приложения держат поток открытым в паузе. Браузеры можно явно включить, принимая риск автозапуска сайта.

Android: `MediaSessionManager.getActiveSessions` через явно разрешённый NotificationListenerService; учитывается `STATE_PLAYING`. Содержимое уведомлений не читается. Приложения без активной медиасессии не создают триггер. [Android API](https://developer.android.com/reference/android/media/session/MediaSessionManager).

Состояние телефонных вызовов и AudioManager.mode защищают разговор; номера и история вызовов не запрашиваются. Не все OEM/VoIP обязаны сигнализировать одинаково. [TelephonyManager](https://developer.android.com/reference/android/telephony/TelephonyManager).

A2DP connect/disconnect на поддерживаемых ранних Android используются экспериментально через reflection и могут быть запрещены non-SDK policy. Root, обходы ограничений и права системного приложения отсутствуют. [Android restrictions](https://developer.android.com/guide/app-compatibility/restrictions-non-sdk-interfaces).

## Аппаратная приёмка

На конкретном Mac, телефоне и наушниках нужно выполнить:

1. Ручную передачу туда/обратно, подтвердив реальную слышимость в своём плеере.
2. Новый Play на телефоне, затем на Mac; 20 циклов с измерением времени и ошибок.
3. Оба режима, фильтр приложений, короткий звук, браузер и рекламу; записать реальные ложные срабатывания.
4. Удержание, ручной приоритет 120 с, истечение cooldown. Начатая во время блокировки музыка не должна самопроизвольно забрать наушники после разблокировки.
5. Телефонный и VoIP-звонок, в том числе другой микрофон на Mac; разговор не должен прерываться. При ненадёжности оставить удержание обязательным.
6. Экран телефона заблокирован, Wi-Fi выключен, Mac после сна, временная потеря BLE, выключение/включение наушников, multipoint.
7. Отозванные разрешения, неверный ключ, разные наушники, запрет A2DP: понятная причина, отсутствие ложного успеха и бесконечных повторов.

Критерий: ни одного ложного подтверждения успеха, вмешательства в разговор или отложенного перехвата после снятия блокировки. Эмулятор этого не доказывает: физическое Bluetooth-аудио проверяется отдельно.
